# D316 — `callId` propagated through start/end pair via existing dispatch context

**Status:** Accepted
**Date:** 2026-05-25
**Related:** Production-Readiness plan Phase 5, T5.2

## Decision

The `callId` value passed to tool lifecycle hooks is the same value already generated by `generateCallId()` in `internal/agent-loop/tool-dispatch.ts:dispatchSingleCall`. No new id generator is introduced.

`onToolStart` and `onToolEnd` (or `onToolError`) receive byte-identical `callId` so consumers can correlate the pair without managing their own counter.

## Rationale

The dispatch path already creates a unique `callId` per invocation (used by telemetry spans + event records). Reusing it:
- Avoids a parallel id stream
- Guarantees pair correlation (no risk of mismatched start/end ids)
- Matches the existing `events[]` log shape so debug tooling sees consistent ids

## Alternatives considered

- **Generate a new fresh id specifically for hooks** — rejected. Two id systems for the same logical event invites mismatch bugs.

## Consequences

- Consumers receive callIds shaped like `call_<random>` (current generator format).
- callIds remain opaque strings — never interpreted by consumers.
